# Decisions

One line per decision and why. Newest at the bottom.

- 2026-11-18: Repository split into `backend/`, `frontend/` and `eval/` so each part builds and deploys on its own.
- 2026-11-18: Backend package is `ke.sauti.hms`, organised by feature (common, security, staff, patient, visit, capture, note, ai, medication, billing, audit, jobs, integration).
- 2026-11-18: Login uses server sessions stored in PostgreSQL (Spring Session JDBC), not tokens, so logout and account disabling take effect at once; the OAuth2 resource server starter was removed.
- 2026-11-18: Secrets come only from environment variables; `.env.example` lists the names, never values.
- 2026-11-19: Local object storage uses SeaweedFS (S3-compatible) instead of MinIO, because MinIO stopped publishing container images; the app only speaks the S3 API, so the store can be swapped without code changes.
- 2026-11-19: Profiles: `dev` is the default (compose services, fakes), `test` for automated tests, `demo` for real services. `sauti.required-env` lists the variables a profile needs, and startup fails naming every missing one.
- 2026-11-19: Container images are pinned to exact tags (PostgreSQL 18.7) in both compose and Testcontainers, so dev, tests and CI run the same database version.
- 2026-11-19: Facility settings live in their own `facility` package; the table is limited to one row with a unique index on a constant, and V1 seeds a demonstration facility.
- 2026-11-19: Errors use one `ApiError` shape built only in `BaseExceptionHandler`; every handler extends it, feature code throws `ApiException` subclasses, and a feature adds its own handler only for a genuinely new exception type.
- 2026-11-19: Client errors log one WARN line without a stack trace; server errors log at ERROR with the stack trace; exception messages from libraries never reach the response.
- 2026-11-19: An incoming `X-Request-Id` is reused only if it is a canonical UUID; anything else is replaced so outside text never reaches the logs.
- 2026-11-19: Entity ids are version 7 UUIDs (time-ordered, index-friendly); timestamps come from the injected `Clock` through JPA auditing.
- 2026-11-19: Java quality gates run inside `./mvnw verify`: Spotless with palantir-java-format, compiler warnings as errors (`-Xlint:all` minus serial and processing), Error Prone, and a JaCoCo coverage report with no threshold yet.
- 2026-11-19: Feature packages are the first package below `ke.sauti.hms` (common, facility, security, staff, patient, visit, capture, note, ai, medication, billing, audit, jobs, integration). ArchUnit enforces that controllers never use repositories and that a feature uses only its own repositories; other features' data goes through their services.
- 2026-11-19: Frontend is Vite + React 19 + TypeScript (strict) with React Router, TanStack Query, React Hook Form and Zod; TypeScript stays on 6.0 until typescript-eslint supports 7. Dependencies are exact pins at least two weeks old, installed with `npm install --before`; minimatch is overridden to 11.0.4 for a moderate advisory in lint tooling.
- 2026-11-19: The dev proxy forwards `/api` and, in development only, `/actuator` (for the health check on the home page) to the backend, so the browser sees one site.
- 2026-11-19: Security scanning: gitleaks on every PR and push to staging (full history), CodeQL security-extended for Java and TypeScript (no build needed), Dependabot weekly for Maven, npm, Actions and compose images with a 14-day cooldown and grouped minor/patch updates, plus Dependabot security updates (not delayed). GitHub secret scanning and push protection stay on.
- 2026-11-19: Staff emails are stored trimmed and lower-case (enforced by a check constraint), so one unique index covers case-insensitive uniqueness; doctors and nurses must have a licence number.
- 2026-11-19: Spring Session's PostgreSQL schema is copied unchanged into a Flyway migration (V3) and `spring.session.jdbc.initialize-schema` is `never`, so Flyway owns every table.
- 2026-11-19: Audit and access-log rows are immutable entities behind insert-and-read-only repositories; `AuditService` and `AccessLogService` require the caller's transaction (`Propagation.MANDATORY`) and fill in time, actor, request id and client address themselves. A failed login must record its audit row without throwing inside the transaction, or the rollback erases it.
- 2026-11-19: The audit actor comes from any security principal implementing `AuditActor`, so the audit package never depends on staff. Behind the hosting proxy, deployment must set `server.forward-headers-strategy` for the client address to be right.
- 2026-11-19: Sensitive columns use AES-256-GCM with a fresh 12-byte nonce, stored as `[key version][nonce][ciphertext + tag]` with the version byte inside the tamper check; lookups of encrypted values use a separate HMAC-SHA256 key. Startup fails if a key is missing, is not 32 bytes of Base64, or if both keys are equal.
- 2026-11-19: Encrypted fields opt in with `@Convert(converter = EncryptedStringConverter.class)`; Hibernate gets the converter from Spring. A value is not yet tied to its column (copying ciphertext between encrypted columns would go unnoticed); that needs one converter per column and is left until patient data arrives. Only key version 1 exists; rotation adds old keys by version without changing the stored layout.
- 2026-11-19: Dev and test profiles carry fixed, non-secret keys so local data survives restarts; every real deployment must set `APP_ENCRYPTION_KEY` and `HASH_KEY`, which the demo profile requires.
- 2026-11-20: Passwords use Spring's Argon2id encoder at OWASP's minimum settings (salt 16, hash 32, parallelism 1, 19,456 KiB, 2 iterations), with Bouncy Castle 1.86 (1.87 was under two weeks old). Each hash records its settings, so they can be raised later.
- 2026-11-20: Authenticator codes are our own RFC 6238 code (HMAC-SHA1, 30-second steps, 6 digits), tested against the Appendix B vectors, instead of a library. A code is accepted one step either side of now, only once: the step must be newer than `last_code_step`, and the entity version check stops two concurrent uses of one code. `CodeCheck.require` gives signing flows a 403 guard.
- 2026-11-20: Login is two steps over the server session: the password step leaves a 5-minute note (staff id, whether this is authenticator setup) and only the code step logs in, changing the session id first. The authenticator secret lives encrypted on `staff`, never in the session, because session data is stored unencrypted.
- 2026-11-20: Every refused login (unknown email, wrong password or code, locked, disabled) gets one generic 401 `LOGIN_FAILED`; unknown emails are checked against a dummy Argon2 hash so timing reveals nothing. Five failures in a row (passwords and codes together) lock the account for 15 minutes. Login steps return their outcome instead of throwing, so the failure count and the `LOGIN_FAILED` audit row commit.
- 2026-11-20: The session principal is a small `StaffPrincipal` whose name is the staff id, so Spring Session indexes sessions by staff id for ending them when an account is disabled. Until a one-time password is changed, every API call outside `/api/auth` gets 403 `PASSWORD_CHANGE_REQUIRED`. Spring Boot's generated in-memory user is excluded.
- 2026-11-20: Bouncy Castle moved to 1.87 nine days after release, inside the two-week rule, because Qodana reported 1.86 as vulnerable; known vulnerabilities override the waiting period, as Dependabot security updates already do.
- 2026-11-20: Sessions end after 15 minutes idle (`spring.session.timeout`; Spring Session ignores `server.servlet.session.timeout`) and 8 hours after login however active (`SessionAgeLimitFilter`, on the injected clock). The session cookie is HttpOnly, Secure and SameSite=Strict; cookie flags are tested against a real server because MockMvc rebuilds `Set-Cookie` headers and drops attributes.
- 2026-11-20: CSRF uses `csrf.spa()` with one shared cookie repository (readable `XSRF-TOKEN`, Secure, SameSite=Strict, Path=/), so anonymous requests create no session. Our login is not one of Spring's filters, so `AuthController` replaces the token at login and logout itself, with an eager request handler so the new cookie is in the same response. A bad token is 403 `CSRF_TOKEN_INVALID`, so the front end can reload instead of showing "no access".
- 2026-11-20: Filter-level 401 and 403 go through Spring MVC's exception resolver, so they get the same `ApiError` body. Role rules sit on endpoints with `@PreAuthorize`; `AccessRulesTest` is the table every new endpoint adds a row to. API responses carry HSTS (1 year), nosniff, frame DENY, no-referrer, a CSP allowing nothing (the API only serves JSON) and a Permissions-Policy allowing only this site's microphone; the front end's own CSP belongs with its hosting.
- 2026-11-20: The first admin comes from `FIRST_ADMIN_EMAIL`/`FIRST_ADMIN_PASSWORD` only while the staff table is empty, so restarts never add admins or reset passwords; without them the app warns and starts. Dev has a fixed local admin. New accounts get a server-generated 16-character one-time password (no look-alike characters), shown once in the create response; both must change it and set up an authenticator at first login.
- 2026-11-20: Disabling an account publishes `StaffDisabledEvent`; after the transaction commits, security deletes all that person's sessions found by principal name (the staff id), so `staff` never touches sessions and a rolled-back disable logs nobody out. An admin cannot disable their own account.
- 2026-11-20: `/api/admin/**` needs ADMIN as a URL rule as well as `@PreAuthorize`, because method security runs after the request body is read and validated; without the URL rule a non-admin got a 400 with validation details instead of a 403.
- 2026-11-20: A logged-in person refused with 403 (role rule or bad CSRF token) writes `ACCESS_DENIED` with method and path, from Spring Security's authorization events, in its own short transaction. Tests never use Spring Security's `csrf()` helper: it swaps the CSRF token store inside the shared filter for the rest of the cached context; `ApiBrowser.validCsrfToken()` sends a matching cookie and header instead.
- 2026-11-20: The front end has one API client: it always sends cookies, copies `XSRF-TOKEN` into `X-XSRF-TOKEN` on changing requests (fetching a token first if there is none, retrying once on `CSRF_TOKEN_INVALID`), and reports a 401 (outside the login steps) and `PASSWORD_CHANGE_REQUIRED` to the app, which empties the session cache or opens the password page.
- 2026-11-20: "Who is logged in" is one TanStack Query entry from `GET /api/auth/me` (401 means nobody), so a reload keeps the person logged in. Every logged-in page is declared with the roles allowed; the guard sends logged-out visitors to login (returning afterwards, same-site paths only), one-time passwords to the password change, and wrong roles to a no-access page. The backend still checks every request.
- 2026-11-20: Ten minutes without input logs out (the server's 15-minute timeout backs it up); work without input, such as recording, calls `reportActivity()`. Logout clears every cached query so no patient data stays in memory. The setup QR code is drawn in the browser as SVG, so the secret never leaves the page.
- 2026-11-20: Patient identifiers (phone, national ID, SHA number, next of kin phone) are encrypted; phone and national ID also get keyed hashes of the normalised value (phones as 254 + 9 digits) for exact search and duplicate checks. Names stay plain, with a trigram index on `lower(full_name)`. Searches are audited with the route taken and the result count, never the query.
- 2026-11-20: Registration refuses a national ID already on file (409 with the patient). A matching phone also gives 409 with the matches, but reception may confirm a different person (families share phones), and the audit row records that. Patient numbers come from a database sequence and show as SH-000123.
- 2026-11-20: Reception registers patients; reception, nurses, doctors and cashiers search and read them; admins do not. Allergies are for nurses and doctors (care-team check in issue 18). Allergy entries are never edited or deleted, only marked entered in error with a reason; "no known allergies" is its own entry, retired automatically when an allergy is recorded. Role rules are URL rules too, so a refused role never sees validation errors.
- 2026-11-20: Optional boolean flags in request bodies are `Boolean`, not `boolean`: Jackson 3 fails on a missing primitive by default, which turned a missing flag into a 400 for the whole request.
- 2026-11-20: Visit status changes only through `VisitService.changeStatus` (and `take`), checked against one map of allowed moves to roles in `VisitWorkflow`: a move not in the map is 409, the wrong role 403. While a patient is in triage or with a doctor, only the person holding them may move the visit on. Every change writes `visit_status_history` and an audit row; cancelling needs a reason.
- 2026-11-20: Concurrency: every change loads the visit with `select ... for update`, so two doctors taking one patient go one after the other and the second gets 409. Queue numbers come from one atomic `insert ... on conflict do update ... returning` on a per-day counter row. A patient has at most one visit in progress (partial unique index). Days are the facility's local days (`sauti.time-zone`, Africa/Nairobi).
- 2026-11-20: Care assignments are created only by the workflow: reception on opening, the nurse or doctor on taking; every status move ends the open ones. The reason for visit is encrypted and not returned by the visit endpoints; clinical reads go through the access policy (issue 18).
- 2026-11-20: Clinical data goes through one `AccessPolicy` (in `visit`, beside the care assignments it reads). A role table says which roles may see which data at all (doctors everything; nurses reason for visit, allergies, vitals, notes and prescriptions; reception the reason for visit; cashiers prescriptions; admins nothing). Within that, the person needs an open care assignment, or one ended under 24 hours ago; a doctor on a current visit may also open past signed notes and prescriptions of the same patient. Every refusal is a 403 audited as `ACCESS_DENIED` in its own transaction (so the rollback does not erase it); every allowed read writes an `access_log` row.
- 2026-11-20: Patient-wide data (allergies) needs a recent care assignment on any visit of that patient. An unknown patient or visit is 404 before the policy runs.
- 2026-11-20: Queue screens poll every 5 seconds (TanStack Query `refetchInterval`) and refresh all queues at once after any visit change; they show queue number, name, patient number and waiting minutes only. Taking a patient someone else took first shows "Someone else has already taken this patient." Reception opens a visit and sends it to triage in one step.
- 2026-11-20: `ApiRequestError` keeps the whole response body, so errors with extra fields (the duplicate-patient matches) can be read by the screen that needs them.
- 2026-11-20: Recording consent is append-only: each decision (AGREED, REFUSED, WITHDRAWN, with who gave it and the wording version shown, for example v1-sw) is a new row, and the latest for a visit and purpose counts. `ConsentService.requireAgreed` is the guard capture must call when a recording starts and for every piece; a withdrawal publishes `ConsentWithdrawnEvent` so capture can stop. Recording and reading decisions needs the care team (`ClinicalData.CONSENT`; reception, nurses and doctors). Wording lives in versioned files `consent/v1-sw.txt` and `consent/v1-en.txt`, marked as demonstration wording.
- 2026-11-20: Audio pieces go to S3-compatible storage through `AudioStore` (AWS SDK v2 sync client, path-style, Netty async client excluded), always encrypted with the app key before upload and decrypted on read, so the bucket holds only ciphertext. SeaweedFS locally (compose), Cloudflare R2 in the demo; tests run a SeaweedFS container. The bucket is created at startup only in development and tests.
- 2026-11-20: A recording (capture session) starts only for the right role for its purpose (reception for RECORD_RECEPTION, nurses and doctors for RECORD_CONSULTATION), a member of the visit's care team, an open visit, an AGREED consent, and no other recording running for that visit and purpose (partial unique index). A consent withdrawal stops running recordings after it commits.
- 2026-11-20: Background work runs on a `job` table in PostgreSQL, not a message broker. The worker claims up to 5 due jobs in one `update ... where id in (select ... for update skip locked) returning`, runs each handler, and records the outcome: DONE; `JobFailure.RetryAfter` waits the provider's delay without using an attempt; `JobFailure.Permanent` fails at once; anything else retries after 5 s, 30 s, 2 min, 10 min and fails after 5 attempts. Jobs left RUNNING past their 5-minute lock return to the queue every minute. Jobs are queued in the caller's transaction, and every handler must be safe to run twice. Handlers run one after another on the scheduler thread; more throughput comes from more instances.
- 2026-11-20: Transcription goes through a `SpeechToText` port; the fake adapter is the default (`sauti.transcription.provider=fake`) until Groq is configured (issue 27). `TranscriptFilter` drops silence, repetition loops, phantom phrases and repeats, and grades segments LOW (avg_logprob < -0.8), REVIEW (< -0.5, or containing a number, a medicine name or a negation such as si, sina, hakuna, no, not) or HIGH. The prompt is a medicine glossary plus the last 200 characters heard.
- 2026-11-20: Pieces arrive at `PUT /api/captures/{session}/pieces/{seq}` (raw audio body; checksum, duration and offset in headers). Only the person recording may send pieces; consent is checked for every piece; a repeat with the same checksum is a harmless 200 and a different piece under the same number a 409; an erased recording answers 410. Storing, recording and queueing transcription happen together. The TRANSCRIBE job replaces a piece's segments (safe to run twice) and completes the recording once every expected piece is done.
- 2026-11-20: Transcripts and audio are read through the access policy; reception and nurses may now read `TRANSCRIPT` and `AUDIO` too (care team still required), since the person recording watches the live transcript. Opening a transcript (the first fetch, without `after`) writes an access-log row; the 2-second polls after it do not. Every audio play writes one; audio is sent decrypted with `Cache-Control: no-store`.
- 2026-11-20: Erasing a recording marks it ERASED, deletes its segments, marks its pieces ERASED and cancels their queued transcriptions in one transaction; the encrypted audio files are deleted from storage after the commit, so a rolled-back erase never loses audio. The audit row counts pieces and segments, never content. Uploads and reads on an erased recording answer 410.
- 2026-11-20: The browser recorder (`features/recorder`) calibrates the room's quiet level for a second, reads loudness every 100 ms, and cuts a piece after 20 s at the first 0.6 s pause or at 45 s, by starting a new `MediaRecorder` on the same stream before stopping the old one (each piece is a complete, playable file). Silent pieces are dropped; kept pieces are numbered contiguously, so the count sent at stop is what the server should expect. Pieces wait in IndexedDB until the server has them; the uploader sends oldest first with backoff 2 s doubling to 30 s, drops a recording's pieces on 410 and a refused piece on other 4xx. On page load pieces older than a day are deleted and the rest resume; on logout pending pieces are sent for up to 5 s, then cleared from the device.
- 2026-11-20: The transcript panel polls every 2 seconds for lines after the last one received while recording, and after Stop until the recording is complete. LOW lines are lighter with a dotted underline and an "unsure" marker; REVIEW lines are highlighted with a "check" marker. Clicking a line plays the piece from that moment (audio fetched decrypted, never cached). Erasing asks for confirmation first.
- 2026-11-20: The Groq adapter posts to `/audio/transcriptions` with `whisper-large-v3`, `verbose_json`, segment timestamps, temperature 0, the language hint and the prompt (cut to its last 600 characters, under Whisper's 224-token limit), using RestClient directly for the per-segment confidence numbers. 429 waits for Retry-After (20 s if absent); timeouts, connection failures, 5xx, 401 and 403 are temporary (a wrong key can be fixed without losing jobs); other 4xx are permanent. It is used only when `sauti.transcription.provider=groq` (the demo profile, which requires `GROQ_API_KEY`); development and tests keep the fake.
- 2026-11-20: Vitals are recorded at `POST /api/visits/{visit}/vitals` by the nurse holding the patient while the visit is IN_TRIAGE; saving moves the visit to WAITING_DOCTOR in the same transaction (through the workflow, which takes the visit lock). Limits: temperature 30 to 45 °C, pulse 20 to 250, breathing 4 to 80, systolic 50 to 260 above diastolic 20 to 160, SpO2 50 to 100, weight 0.5 to 300 kg and height 30 to 250 cm optional; the form checks the same limits. Readings are never edited, a new reading is a new row. Reads go through the access policy and are access-logged. The triage queue no longer has a "Send to doctor" button: the nurse opens the patient, sees the allergy list beside the form, and saving the vitals sends them on.
- 2026-11-20: One note per visit (`clinical_note`), sections encrypted (presenting complaint, history, examination, assessment, plan). `PUT /api/visits/{visit}/note` saves the draft with the version the editor holds: a different current version, or no version when a note already exists, is 409 `STALE_VERSION`, so two tabs never overwrite each other. Saves and signs lock the note row. Signing (`POST .../note/sign`) needs the version the doctor saw, assessment and plan (422 otherwise) and a fresh authenticator code (403 otherwise); it is audited `NOTE_SIGNED`, and after it every save is 409 `CONFLICT`. Addenda (`POST .../note/addenda`) only on signed notes, audited `NOTE_ADDENDUM_ADDED`, never changed. Only the doctor on the care team writes; nurses on the care team read. Once AI help is used, the note stays marked `ai_assisted`. `GET /api/patients/{patient}/history` returns the patient's signed notes to a doctor looking after a current visit of that patient, each one access-logged; prescriptions join it with issue 41.
- 2026-11-20: The note editor (`features/notes`) keeps its own copy of the draft and saves it 2 seconds after typing stops, sending the version it holds; saves run one at a time, and a failed save (not a conflict) is tried again after 5 seconds. A 409 stops autosaving and shows a warning with a "Reload the note" button; the unsaved typing stays on screen until the doctor reloads. Signing first saves what is on screen, then signs that exact version with an authenticator code; the backend's own reason is shown for a wrong code. The doctor's visit page puts the note (with a History tab of earlier signed notes, no old audio or transcripts) beside the recording panel and live transcript; the editor stays mounted on the History tab so typing is never lost.
- 2026-11-20: The clinical AI calls Groq's OpenAI-compatible chat API directly with RestClient (like the Whisper adapter) rather than through Spring AI: one less dependency, and the same timeout and error handling as the transcriber. Model pinned to `openai/gpt-oss-120b`, temperature 0, JSON output, prompt `prompts/summary-v1.txt`; the fake is used unless `sauti.ai.provider=groq` (the demo profile). `POST /api/visits/{visit}/summary` checks the doctor on the care team (access-logged as opening the transcript) and that consultation consent still stands, reads the non-erased consultation transcript in a short transaction, then calls the model outside any transaction: 20 s read timeout, one retry, then "Summary unavailable". Every claim is checked in plain Java (`ClaimChecker`): quote present (ignoring case, punctuation and spacing, whole words), negation consistent (English and Swahili negation, including sija-/haja- verbs), every number in the claim said in the quote (digits, English or Swahili words), and CHECK_AUDIO when the quote comes from a LOW or REVIEW line. Every call writes an `ai_request` row (model, prompt version, status, duration, and the claims and checks as encrypted JSON).
- 2026-11-20: Accepting summary claims goes through `POST /api/visits/{visit}/summary/{request}/accept` with claim positions and the note version the editor holds. The server reads the claims and verdicts from its own `ai_request` row, never from the browser, and refuses the whole request (422) if any claim failed the checks; accepted claims are added as new lines at the end of their note sections, the note is marked `ai_assisted`, and the acceptance is audited `AI_CLAIMS_ACCEPTED` (count only). The note's own rules apply: doctor on the care team, not signed, current version. The editor saves the doctor's typing first, accepts, then shows the note as the server returns it. In the drawer, a claim from a LOW or REVIEW line can be accepted only after its words are played; "Accept all" takes only claims that passed and, where needed, were listened to. The fake model now adds one planted claim quoting words nobody said, so the rejected case is always on screen in development.
- 2026-11-20: Arrival tickets (`queue_ticket`) in four lanes, each numbered from 1 per day: P (pre-registered), R (returning), N (new), E (emergency), codes such as N-007. Reception calls the next ticket with one locked query (`FOR UPDATE SKIP LOCKED`, so two desks never get the same ticket): a new ticket waiting 15 minutes or more first, then pre-registered and returning, then new, each in arrival order. Emergency tickets never go through reception's call: nurses and doctors see them at the top of their screens and one attends. Opening a visit for a called ticket (or a waiting emergency) sets the visit's arrival time to the ticket's and marks the ticket served, in the same transaction. Reception can cancel a ticket whose patient did not come. `GET /api/public/queue-board` (no login) returns ticket codes only: the last five called and those still waiting, never emergencies; the `/waiting-area` page shows it, refreshing every 5 seconds.
- 2026-11-20: Pre-registration (`/pre-register`, reached by QR code) posts to `POST /api/public/pre-registrations` without login. It only saves: it never looks up a patient and answers with the new P ticket's code alone, so it cannot reveal anyone's data. Name, phone and reason are encrypted; the phone and IP hashes carry their own prefix so they never match a patient record's hash. Limits: 3 per phone per day and 10 per IP address per hour (429). No national ID on the public form. Reception opens an entry by its ticket code (`GET /api/pre-registrations/{code}`, audited `PRE_REGISTRATION_OPENED`) to pre-fill the registration form, where each field the patient typed is marked "patient-entered". A job queued at creation deletes every entry at the end of its day, used or not. Public tickets have no `issued_by`.
- 2026-11-20: The national client registry and SHA eligibility sit behind ports (`ClientRegistry`, `Eligibility`) with fakes over twenty made-up people (national IDs 30000001 to 30000020; odd IDs eligible, even not, anyone else unknown; 39999999 acts as a service that is down), switched by `sauti.registry.provider`. Reception looks a national ID up (`GET /api/registry/lookup`, audited without the number): a hit fills name, date of birth and sex, marked "from the registry"; a miss or no answer (503) means typing them. The ID number is always typed. A patient registered with a national ID gets a PENDING eligibility answer and an `ELIGIBILITY_CHECK` job in the registration transaction (through a `PatientRegisteredEvent`, so the patient feature does not depend on this one); the job stores ELIGIBLE, INELIGIBLE or NOT_FOUND, or UNAVAILABLE and retries. `GET /api/patients/{id}/eligibility` (reception and billing) feeds a badge that refreshes every 3 seconds until answered. Eligibility never blocks care: no workflow step reads it.
- 2026-11-20: Voice drafts for reception's free-text fields (reason for visit, residence, next of kin name; never name, date of birth, phone or ID numbers). While recording, focusing a field cuts the current piece and tags the next with that field (`X-Piece-Field`, stored on `audio_piece.field_tag`). After a tagged piece is transcribed, a `DRAFT_FIELD` job asks the model for `{value, quote}` (prompt `field-draft-v1`, outside any transaction) and keeps the draft only if the quote is in that piece's transcript; every call writes an `ai_request` row of kind FIELD_DRAFT, dropped drafts included. Drafts live in `field_draft` (value and quote encrypted), never in the patient record: reception sees a greyed draft under the field with its quote and a play button, "Use this" copies it into the field, and saving goes through the normal endpoints (`PUT /api/visits/{id}/reason`, `PUT /api/patients/{id}/contact`) before the draft is marked confirmed. The triage nurse confirms the reason for visit with the patient (`POST .../reason/confirm`); any later change clears the confirmation. The reason column is now updatable for this.
- 2026-11-20: The visit stores `registration_started_at` (when its ticket was called, or when the visit opened without one) and `registration_completed_at` (the first move to triage). The waiting-time report (`GET /api/admin/reports/waiting-times`, administrator only, at most 92 days) is one SQL query over visits, tickets and the status history: per lane (NO_TICKET without one) and hour of arrival in facility time, the median and 90th percentile (`percentile_cont`) in minutes of the wait for the desk, registration, the wait for triage, the wait for a doctor, and door to doctor. A stage no visit reached is empty. Only timings leave the database. It is the administrator's home page; the scripted timing study is described in `docs/waiting-time-study.md`.
- 2026-11-23: Tomcat moved to 11.0.29 ahead of Spring Boot 4.1.3, which still manages 11.0.27, because Qodana reported critical vulnerabilities in 11.0.27. Logback stays on 1.5.38 for now: it is the newest 1.5 release, and 1.6 is outside what Boot 4.1 manages. The android-json finding is in test code only. Qodana now keeps its results file on each CI run, so findings can be read without signing in to Qodana Cloud.
- 2026-11-23: The admin home has a staff accounts screen over the existing `/api/admin/staff` endpoints. The one-time password stays only in the page's memory until the admin confirms they passed it on, and is not kept in the request cache. Disabling asks for confirmation and is not offered for your own account.
- 2026-11-23: The medicine list (`data/medicines-v1.csv`, 51 entries, and `data/allergy-groups-v1.csv`) is demonstration data, not clinically reviewed. A Java Flyway migration loads it, with a checksum over the lines so an edit to a loaded file stops startup; a change means a new file version and migration. Each medicine has one group, used for both the allergy-group and same-group rules in #42. A visit has at most one prescription that is not cancelled. Draft items may have missing details because rule R1 blocks signing later. Only the doctor on the visit can change a draft, only while the patient is with them, and every change carries the revision the screen read. Free-text instructions, alert messages and override reasons are encrypted.
- 2026-11-23: Prescription safety (#42) runs eight plain Java rules on every change to a draft, in `medication/safety`. R1 missing details blocks signing and can only be cleared by filling them in. R2 allergy and R3 allergy group block signing unless overridden with a reason of at least 10 characters and an authenticator code. R4 duplicate, R5 same group (supplements ignored), R6 quantity, R7 allergies never asked and R8 allergy not recognised need review. R8 was added beyond the plan: a misspelled or unlinked allergy could otherwise pass the group check unnoticed, so it asks for a check by hand. Allergy matching uses whole words with the aliases sulfa and NSAID. Aspirin moved to the NSAID group in V21 (`medicines-v2`). Signing checks the rules before the code and needs no open alert; a signed prescription is final and can only be cancelled with a code. Alerts are hidden from cashiers. The rules are not clinically reviewed, and there are no drug interaction or penicillin-cephalosporin cross-reactivity checks.
- 2026-11-23: Spoken instructions (#43) are built only from a signed prescription's values and the versioned wording in `templates/instructions-v1`, with numbers as words and digits after a point read one by one. The doctor's free-text instructions are not spoken. The verb follows the route, so creams and injections are never described as swallowed, and every 8 hours in Swahili is "kila baada ya saa nane" because "kila saa nane" can be heard as two o'clock. The default `sauti.speech.provider=browser` sends text for the browser to speak; `azure` needs `AZURE_SPEECH_KEY` and `AZURE_SPEECH_REGION`. Azure audio is cached encrypted in object storage under a hash of text and voice. If the server voice fails the browser speaks instead, and if the device has no voice for the language, staff are asked to read the text aloud. The wording is demonstration wording and needs review by a Swahili-speaking clinician.
- 2026-11-23: Billing (#44). `POST /api/visits/{visit}/finish` is the only way to payment: it needs a signed note, no running recording, and a signed prescription if it has medicines, then builds the invoice from the consultation fee plus each line at list price. Prices are copied onto the invoice. A signed line with no quantity stops finishing instead of billing a guess. The general status endpoint now refuses WAITING_PAYMENT and DONE, so no visit can skip its bill. Cash pays the full total and ends the visit; insurance leaves the invoice INSURANCE_PENDING and ends the visit. Each settlement locks the visit and carries an idempotency key, and a partial unique index allows one live payment per invoice. The cashier sees medicine name, strength, quantity and price, never a dose, note, allergy or reason for visit; medicine names are encrypted on the invoice and every read is access-logged. The fee is `CONSULTATION_FEE_KES`, a demonstration 500 until the facility sets it. Visits already in WAITING_PAYMENT before this change have no invoice and would need handling if real data existed.
- 2026-11-23: M-Pesa (#45) has four states: PENDING, PAID, FAILED and UNCONFIRMED. The fake gateway is the default until Daraja keys are set (`MPESA_PROVIDER=daraja`). Daraja's status query reports only how a prompt ended, so PAID needs both that query's success and a callback amount equal to the bill. A callback alone never pays. A wrong amount, a lost connection while sending, an unknown result code, or no clear answer after 10 minutes becomes UNCONFIRMED, and a successful prompt whose callback never arrived also ends there, because its amount cannot be confirmed. An open or unconfirmed M-Pesa payment blocks every other payment on that invoice, because the customer may already have paid. The cashier settles an unconfirmed payment from the M-Pesa statement with a reason (encrypted) and, if received, the receipt. The phone number is used for the prompt and never stored. The callback path holds a secret of at least 32 characters, and its body is read as text so a malformed request cannot log that path. M-Pesa takes whole shillings only, so another total is refused rather than rounded.
- 2026-11-23: Database rights and rate limits (#46). Flyway migrates as the database owner; the app logs in as a member of the `sauti_app` role, which can use normal tables but cannot change the schema, read Flyway's history, or update, delete or truncate `audit_event` and `access_log`. Demo and production need `FLYWAY_USERNAME` and `FLYWAY_PASSWORD`; local development still uses the single compose account. Bucket4j limits are listed in `RateLimits` and `RateLimitConfiguration`: login, the code step, audio uploads, the summary and every public endpoint, per address and, where someone is known, per account. Address limits are generous because a hospital can share one public address. Only wrong signing codes count against that limit (10 per 15 minutes per account), so a busy doctor is not slowed. Limits are held in each app instance's memory. Behind a hosting proxy `FORWARD_HEADERS_STRATEGY=native` is required, or every user counts as the proxy's address; it must stay off without a trusted proxy, or clients could fake their address.
- 2026-11-23: Security review (#47). The OWASP ZAP 2.16.1 baseline scan of the running API found no high or medium issues. Its low findings are accepted: `XSRF-TOKEN` must be readable by the page for CSRF protection, the cross-origin isolation headers are not needed by a same-site API, and the image version is pinned on purpose. The review found and fixed one real problem: a refused anonymous request created a database session, so anyone could fill the session table. The saved-request cache is now off. A test proves patient names and reasons for visit do not reach the logs, including on refused requests. The scan is a manual GitHub workflow. It does not log in and sends no attacks. The API sends its security headers, with HSTS only over HTTPS; the web pages are not served by the backend yet, so their CSP and microphone policy must be set and checked with the deployment (#51).
- 2026-11-23: Nightly clean-up (#48) runs at 02:30 facility time. It deletes audio of visits whose note was signed over 30 days ago, keeping the transcript; pre-registrations from earlier days; and recording files no live row points to. It never deletes notes, prescriptions, vitals, transcripts or audit rows. Pieces are marked ERASED and committed before their files are deleted, so a failed delete leaves a file the next night's orphan sweep removes. The sweep looks only under `sessions/`, so cached spoken instructions are kept, and skips files under a day old because an upload stores its file before its row commits. Audit rows hold counts and ids only. The 30-day period (`CLEANUP_AUDIO_RETENTION`) is a demonstration value: confirm it against the legal schedule before real use.
- 2026-11-23: Backups (#49). `ops/backup` holds the tools and a nightly GitHub workflow, off until `BACKUP_ENABLED` and its secrets are set. `pg_dump` is piped straight through `age` public-key encryption to a separate private bucket, so no unencrypted dump touches disk; the private key stays offline. Files are kept 35 days and each attempt is recorded in `backup_run` for the status page. Login sessions are left out. Audio files are not in this backup, and `APP_ENCRYPTION_KEY` and `HASH_KEY` must be kept separately or restored data cannot be read. One real restore on local containers took 3.3 seconds, and 25.3 seconds through starting the app, logging in as a doctor and reading the original note. The steps and the record are in `docs/backup-restore.md`.
